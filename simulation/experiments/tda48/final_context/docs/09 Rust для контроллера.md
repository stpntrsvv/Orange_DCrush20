## Зафиксированное решение

По прямому указанию пользователя от 2026-09-24 контроллерная реализация использует
только CMSIS и прямой доступ к регистрам. HAL, LL, Cube-generated runtime,
Embassy, PAC и `embedded-hal` в firmware запрещены. Это архитектурное требование,
а не временный обход отсутствующей поддержки H7R3.

Rust остаётся основным кандидатом для DSP и основной логики. Код проектируется
как `#![no_std]`, без heap и скрытой динамики в аудиопути. Python остаётся
float64-эталоном, генератором коэффициентов и fixtures.

## Силовой выход и реальный динамик

По решению пользователя от 2026-09-25 контроллер не привязывается к TDA2050 или
конкретному силовому модулю. После STM32 используется внешний калиброванный
Class-D с достаточными полосой, током и напряжением, а нагрузкой является реальный
динамик. Class-D рассматривается как исполнитель требуемого напряжения, а не как
часть характера Orange.

На клеммах динамика измеряются напряжение `v_spk` и ток `i_spk`. Они возвращаются
в виртуальную модель TDA2050:

- фактическое напряжение участвует во внешней обратной связи;
- ток управляет current limit/SOA;
- ток и мощность обновляют медленную модель виртуального питания;
- аппаратные защиты и быстрый внутренний контур Class-D остаются физическими.

Широкополосную цифровую петлю нельзя считать мгновенной: ADC, обработка и
DAC/PWM вносят задержку. Первый эталон использует причинную связь
`measurement[n] -> command[n+1]`; затем проверяются устойчивость и ошибка.
Основной кандидат для устойчивой двусторонней границы — пассивные волновые
координаты с явным опорным сопротивлением `R0`:

```text
a = (v + R0*i)/2
b = (v - R0*i)/2
```

Выбор `R0`, знаков, задержки и частоты измерения должен быть подтверждён общей
офлайн-MNA. Простое помещение задержанного тока в алгебраическое уравнение
текущего отсчёта запрещено.

Реактивная модель динамика остаётся в Python как автономный эталон, fixture и
режим разработки без силовой платы. В firmware штатный режим использует реальный
измеряемый порт. Электрические датчики не заменяют кабинетный IR для линейного
выхода, но при прослушивании реального динамика его акустика возникает физически.

Эта аппаратная интеграция выполняется позже. Текущий порядок: закончить полную
самостоятельную модель Orange, динамический mute, сетку проверок, точное
сокращение и контроллерообразный float32; затем проектировать power-port.

## Архитектура

```text
Python float64 reference + fixtures
                 ↓
Rust no_std DSP и управляющая логика
                 ↓
тонкая CMSIS-граница + прямые регистры STM32H7R3
                 ↓
startup / linker / clocks / cache / MPU / DMA / audio IRQ
```

CMSIS используется для определений ядра Cortex-M7, intrinsic, NVIC, SysTick,
DWT, cache/MPU и заголовков устройства. Настройка RCC, DMA, SAI/ADC/DAC,
таймеров и GPIO пишется явно по reference manual и device headers. Никаких
обёрток высокого уровня между кодом проекта и регистрами нет.

## Прямые регистры из Rust

C-прослойка для управления контроллером не нужна. Rust использует
`core::ptr::{read_volatile, write_volatile}`, `core::arch::asm!`, собственную
таблицу векторов и адреса из официального CMSIS device header. Небезопасные
операции изолируются в малом модуле регистров; DSP остаётся safe Rust.

CMSIS-DSP может быть подключён как отдельно собранный объект лишь после сравнения
с чистой Rust-реализацией. Это не разрешение добавить C-драйверы или runtime.

## Требования к realtime-коду

- `no_std`, без allocator, форматирования и panic unwind;
- фиксированные массивы и фиксированная верхняя граница работы на блок;
- никаких HAL/PAC/Embassy/Cube runtime зависимостей;
- коэффициенты генерируются из Python с хешем исходной модели;
- одинаковые fixtures и метрики внутренних состояний для Python/Rust;
- все коэффициенты и состояния имеют тот же стабильный порядок, что float64/f32
  host-модель; Rust не вводит собственную физическую топологию;
- DWT cycle counter настраивается через CMSIS/CoreDebug;
- размещение кода, коэффициентов, состояний и DMA-буферов задаётся linker script;
- D-cache clean/invalidate выполняются явно на границах DMA;
- ISR только подтверждает DMA, переключает буфер и запускает фиксированный DSP;
- ручки публикуются в аудиопуть атомарным snapshot между блоками;
- `fast-math` и ручные intrinsic допускаются лишь после измерения ошибки.

## Структура firmware и ещё не реализованные части

`orange-dsp` и `h7r3-runtime` уже существуют, работают host-тесты, генерация
и RAM-пробы. Дерево ниже также содержит планируемые части: не считать
`power-port`, полный аудиоввод-вывод и готовую CMSIS-упаковку реализованными.

```text
firmware/
  orange-dsp/       # чистый no_std DSP, также тестируется на host
  power-port/       # причинный v/i или wave-port, калибровка и защиты
  h7r3-runtime/     # startup, linker, прямые регистры, IRQ, DMA
  cmsis/            # зафиксированная версия официальных headers/sources
  fixtures/         # бинарные входы и ожидаемые состояния
```

`orange-dsp` не знает о DMA, периферии и размере конкретного аудиобуфера.
`h7r3-runtime` не содержит физической модели, кроме вызова DSP API.

## Аппаратная интеграция: что известно и что ещё проверить

Уже известна плата WeAct STM32H7R3Z8J6, работает ST-Link/AP1 и RAM-only
пуск через `embedded/openocd/run_ram_probe.cfg`. Остальной список — для
полноценного аудиоустройства; RAM-микропроба не закрывает DMA/I/O.

- точный артикул STM32H7R3 и карта памяти;
- boot flow из 64 КБ bootflash и расположение приложения;
- источник тактирования и точная конфигурация 600 МГц;
- аудиоинтерфейс, master clock и размер DMA-блока;
- Class-D: gain, bandwidth, latency, output filter, voltage/current headroom;
- датчики напряжения/тока, аналоговая развязка, ADC timing и знак тока;
- безопасное `R0` и частота двустороннего power-port;
- cache/MPU policy для DMA и коэффициентов;
- probe/debug и загрузка без зависимости от HAL.

Прошивочные crates уже созданы. Язык DSP — Rust `no_std`, низкоуровневое
правило неизменно: CMSIS и регистры, без HAL. Проверки платы и аудиопорта
не должны возвращать работу к уже отменённому этапу выбора языка/skeleton.
